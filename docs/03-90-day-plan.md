# ors 90 天执行计划

> 目标不是"做出求解器"，而是**验证有人在乎"可解释"这件事**，并交付一个能用的 LP 诊断 MVP。
>
> 假设：每周投入 15~20 小时（兼职）或 40 小时（全职）。全职可按 7 周压缩。

---

## 1. 90 天的一句话目标

**让 10 个真实用户，在他们的真实模型上，用 ors 在 1 分钟内定位到不可行的原因。**

成功判定（三项同时满足）：

- [ ] 10 个用户试用，≥ 6 人表示"会继续用"。
- [ ] 3 个可复现的真实案例（脱敏模型 + 报告 + 用户反馈）。
- [ ] LP IIS 在 1000 约束规模上，中位耗时 < 10× 单次 LP 求解。

失败判定（任一触发即复盘转向）：

- 访谈 10 人，< 3 人"最近 3 个月遇到过不可行且没快速定位"。
- IIS 在真实模型上 > 5 分钟，或结果用户看不懂。
- 90 天结束拿不到 3 个案例。

## 2. 周计划

| 周 | 交付 | 验收 |
|---|---|---|
| 1 | 10 人访谈提纲 + 预约；仓库骨架；HiGHS 基线 | 访谈完成 ≥ 4 人 |
| 2 | 访谈收尾；`Model` + `Result` + 状态机 | 能建模、能跑通 HiGHS |
| 3 | MPS 读取；`solve` CLI；与 HiGHS 对拍 | 20 个 Netlib 小模型状态一致 |
| 4 | IIS 删除过滤（LP）；`diagnose()` 返回结构化 IIS | 手写不可行 LP 上正确 |
| 5 | 加性方法；`auto` 策略；性能基准 | 1000 约束模型 < 60s |
| 6 | 证书提取（Farkas）+ 独立验证器 | 随机不可行 LP 验证通过率 100% |
| 7 | 松弛建议（elastic LP）；`Relaxation` | 3 个手写案例给出合理建议 |
| 8 | HTML 报告 + JSON 输出；模型体检 v1 | 报告可独立阅读 |
| 9 | 案例 1（排产/供应链）；用户试用 | 用户能照着报告改对 |
| 10 | 案例 2（配载/能源）；修复反馈 | 报告迭代 2 版 |
| 11 | 案例 3；性能优化（warm start / 缓存） | 中位耗时达标 |
| 12 | 开源发布：README、文档、CI、LICENSE | 公开可 clone、可安装 |
| 13 | 复盘；决定继续/转向；写 v0.2 roadmap | 决策文档 |

**缓冲**：每周留 20% 时间处理意外（数值问题、用户反馈、依赖升级）。

## 3. 用户访谈提纲（30 分钟）

目标：验证痛点、收集脱敏模型、确认付费意愿。**不要推销，只问过去发生的事。**

1. 你最近一次模型跑不出结果，是什么场景？（行业、模型类型、规模）
2. 你怎么判断是模型写错了，还是求解器的问题？
3. 定位花了多久？最后是怎么找到的？
4. 你当时用了什么工具/求解器？为什么没用 IIS？
5. 如果有个工具 30 秒告诉你"这 7 条约束互相矛盾"，对你意味着什么？
6. 你更想要"最小冲突集"，还是"最小修改建议"？为什么？
7. 你的模型一般多大？LP 还是 MILP？变量/约束量级？
8. 你能分享一个脱敏模型吗？（用于案例和回归测试）
9. 你希望它集成在哪里：Python、Excel、Web、还是 CI？
10. 如果免费版只有诊断、付费版有团队协作和报告，你会考虑吗？

**记录模板**：`docs/interviews/YYYY-MM-DD-name.md`，只记原话，不做解读。

## 4. MVP 范围

### 做

- LP 的 IIS（删除过滤 + 加性方法）
- LP 的 Farkas 证书 + 独立验证
- 可行性松弛建议（最小违反量）
- 模型体检（大系数、重复约束、自由变量、矛盾界）
- HTML/JSON 报告
- Python API + CLI
- HiGHS 后端

### 不做（明确推迟）

- MILP 的 IIS（M2 再做）
- 自然语言解释（M2，先用模板）
- 自研求解器内核（M3）
- Web UI / 云端服务（M2）
- Pyomo/JuMP 适配（M2，先支持 MPS + 自有 API）
- Windows 支持（先 Linux/macOS）

## 5. 验收标准（可量化）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| IIS 正确性 | 随机不可行 LP 100% 正确 | 与暴力枚举对比（小规模） |
| IIS 大小 | 中位 ≤ 8 条 | 100 个随机模型 |
| IIS 耗时 | ≤ 10× 单次 LP（≤ 1000 约束） | 同机基准 |
| 证书验证 | 100% 通过 | 独立验证器 |
| 报告可读性 | 3/3 用户能指出该改哪条 | 用户测试 |
| 安装体验 | `pip install -e .` 后 5 分钟内跑通示例 | 新人测试 |

---

## 6. 技术决策（提前定，避免摇摆）

- **后端**：HiGHS（highspy），MVP 阶段不追求增量 API，先每次重建模型。
- **模型层**：自有轻量 `Model`，不做通用代数建模语言。
- **IIS 默认**：小模型删除过滤，大模型加性方法；结果标注 `minimal`。
- **证书**：LP 先做 Farkas；MILP 明确说"无短证书"。
- **解释**：MVP 用模板生成；LLM 解释放 M2，避免过早依赖。
- **存储**：报告 JSON 带 `model_hash`，保证可复现。

## 8. 90 天后怎么走

三种可能：

1. **验证成功** → 进入 M1：MILP 诊断、证书验证、社区、Pyomo 适配。
2. **痛点存在但用户不愿换工具** → 转做"嵌入式"：作为 Pyomo/JuMP 的插件，而不是独立库。
3. **痛点不成立** → 转向 B（领域求解器）或 C（接口层），保留已建的 presolve/证书基础设施。

**关键：无论哪种结果，这 90 天都会留下可复用的资产**——模型层、IIS 引擎、证书验证器、基准体系。这些是求解器内核的前置组件，不会浪费。
